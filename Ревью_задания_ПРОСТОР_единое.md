# Ревью задания: Хакатон ПРОСТОР (единое)

> Консолидированное видение команды. Объединяет разбор задания, данных, шаблонов и проектных решений.

---

## 1. Суть задания

За ограниченное время сделать **работающий MVP** из двух связанных модулей для платформы Газпром нефти **ПРОСТОР** (внутренняя система заказа услуг между «дочками» группы).

| Кейс | Что делает |
|---|---|
| **Кейс 1. Умный конструктор ТЗ** | Собирает техзадание из типовых блоков вместо Word-файла, проверяет полноту, считает % готовности, показывает риски |
| **Кейс 2. ИИ-агент поиска** | Чат-бот: по запросу на естественном языке подбирает услуги, исполнителей, и передаёт результат в конструктор |

**Связка:** поговорил с ботом → нажал «Сформировать ТЗ» → данные из диалога предзаполнились в конструкторе.

---

## 2. Главная идея (как продавать решение)

> Это **не «чатик с ИИ»**, а **цифровизация внутреннего сервиса**.

Сейчас: заявки и ТЗ живут в Word-файлах и переписках, расчёт сроков и стоимости — вручную, нет единого цифрового контура «от заявки до наряд-заказа».

Целевое состояние: структурированная заявка, каталог услуг и операций, ставки, аналитика, прозрачный план/факт.

**Следствие для защиты:** показываем бизнес-эффект (сокращение времени, снижение ошибок), а не «LLM-фичу». LLM — помощник, а не ядро.

---

## 3. Данные (что нам выдали)

6 Excel-файлов из системы + шаблоны ТЗ.

| Файл | Что внутри | Точные цифры |
|---|---|---|
| **0. Компании** | Исполнители: код, название, описание, услуги, рейтинг | **13 компаний**, рейтинг 2–5 |
| **1. Договоры** | Связь контракт → компания | **20 договоров** |
| **2. Договор + РС** | Расчёты стоимости: этапы (иерархия), сроки, документы | **462 заказа**, 1677 этапов |
| **3. Договор + продукты** | Какие продукты в каких договорах | **31 продукт** |
| **4. Продукты + расценки** | Ставки специалистов (L2–L5), единицы измерения | **48 продуктов**, 2780 строк |
| **5. Продукты + Операции** | Детализация: операции внутри продуктов | **35 продуктов**, 318 операций |

### Иерархия связей

```
Company (13) ── Contract (20) ── calc / заказ (462) ── stage / этап (1677)
                                                            └── Product (31–48)
                                                                 ├── price (ставки L2–L5)
                                                                 └── operation (318)
```

### ⚠️ Проблемы качества данных (важно учесть сразу)

- Количество продуктов разное: **31 в договорах, 48 в расценках, 35 в операциях** — несогласованность справочников.
- Есть legacy-элементы с префиксом **«НЕАКТУАЛЬНО»**.
- Дубли имён: «Акселерация бизнес-возможностей» и «Акселерация бизнес-возможностей.» (точка в конце).
- Часть продуктов есть в ценах, но нет в активных договорах (и наоборот).

**Вывод:** без слоя нормализации будут дубли в поиске, странные рекомендации агента и ложные риски. Это первый слой работы.

## 4. Кейс 1 — Умный конструктор ТЗ

### Проблема
ТЗ — статичный Word-файл. Система не может проверить полноту, связать работы со стоимостью, увидеть риски.

### ФТ к MVP (9 пунктов)
1. Выбор типа ТЗ
2. Автосборка структуры по типу
3. Заполнение ключевых полей
4. Выбор этапов и условий
5. Автодобавление требований/разделов
6. Проверка готовности + % готовности
7. Риски и рекомендации
8. Выгрузка итогового документа
9. Аналитические отчёты

### Ключевая особенность
Конструктор проверяет качество: «Подсчёт запасов» + «нужна 3D-модель» → готовность 78%, риски («не указан объект», «3D без этапа подготовки данных»), рекомендации.

### Структура ТЗ (из шаблонов)
Блоки почти одинаковые во всех шаблонах:
```
реквизиты заказа/договора → название работы → заказчик → цели → периметр →
сроки → требования к работам → ожидаемые результаты → документация →
качество → субподряд → подписи
```
Различаются: набор этапов, доменные требования, нормативные ссылки, исходные данные, ставки.

**Вывод:** хранить шаблон не как цельный Word, а как `template + sections + fields + rules + stage presets`.

### Итоговый результат — это пакет документов, а не один файл
- Приложение 1. ТЗ (docx)
- Приложение 2. КП — календарный план (xlsx)
- Приложение 3. РС — расчёт стоимости (xlsx)
- иногда Наряд-заказ

**Вывод:** MVP должен генерировать пакет артефактов, а документы — это представление структурированной заявки, не первоисточник.

## 5. Кейс 2 — ИИ-агент умного поиска

### Проблема
Заказчик не знает точное название услуги, исполнителей, что нужно для заявки, какие аналоги были.

### ФТ к MVP (8 пунктов)
1. Ввод запроса на естественном языке
2. Релевантные услуги с обоснованием
3. Исполнители с обоснованием
4. Рекомендации по заполнению заявки
5. Аналогичные выполненные работы
6. Связанные услуги
7. Черновик заявки из диалога
8. Переход в конструктор с предзаполнением

### Ключевое отличие
Это **консультант**, а не полнотекстовый поиск. Задача — помочь принять решение, а не найти формальное совпадение.

### Типы намерений (для NLU)
Предлагаем 3–5: «поиск услуги», «выбор исполнителя», «запрос аналогов», «формирование ТЗ».

## 6. Архитектура (консолидированное решение)

### Принцип: гибрид — LLM + правила
- **LLM** только для: классификации намерения, генерации ответа с объяснением, суммирования диалога.
- **Правила/данные** для: подбора продукта, исполнителя, расчёта стоимости, рисков, ready score.

Это даёт точность, воспроизводимость и объяснимость (важно на защите).

### Каноническая сущность — `RequestDraft`
Главный объект системы — структурированная заявка:
```
RequestDraft: продукт, заказчик, договор, исполнитель, этапы,
              обязательные данные, риски, готовность, документы, история
```

### Справочные сущности
`Company`, `Contract`, `Product`, `Operation`, `PriceRule`, `Template`, `TemplateSection`, `FieldDefinition`, `ValidationRule`, `HistoricalCalculation`.

### Логические движки
| Движок | Назначение |
|---|---|
| **Search Engine** | подбор продукта, исполнителя, похожих кейсов |
| **Rules Engine** | обязательные блоки, проверки, риски, ready score |
| **Document Builder** | сборка docx/xlsx из структуры заявки |
| **Analytics Layer** | частые услуги, ошибки, этапы, незаполненные поля |

### Формула ранжирования (Кейс 2)
релевантность продукта + наличие в активных договорах + покрытие операциями/расценками + рейтинг исполнителя + наличие аналогов + частота использования.

## 8. Бизнес-правила ДО (субподряд) — уникальные доменные правила

Найдены в аналитическом обзоре, важно для Rules Engine:
- **Хантос**: лимит субподряда ≤ 70% стоимости заказа.
- **Мегионнефтегаз**: работы строго без субподряда.
- **Ангара**: обязательный отдельный расчёт стоимости (РС) субподряда.

Это примеры реальных правил, которые можно показать в демо как работу «умной проверки».

## 9. Объём MVP (что брать, что нет)

### Брать в MVP
- единый веб-интерфейс с двумя сценариями
- поиск услуги по естественному языку
- подбор 1–3 продуктов + исполнителя
- переход в конструктор с предзаполнением
- ready score + 5–10 правил риска
- экспорт ТЗ + хотя бы один сопутствующий документ
- простая аналитика

### НЕ брать в MVP
- реальные корпоративные интеграции
- полный документооборот и workflow согласования
- обучение собственной модели
- весь каталог продуктов

### Периметр: 3–5 продуктов
Рекомендуем: «Подсчёт запасов / ПТД», «Концепт геологии», «Концепт обустройства», «Интегрированный концепт развития» (+ 1 на выбор). По ним есть шаблоны и понятная структура этапов.

## 10. Сквозной демо-flow (сильнейший сценарий для жюри)

1. Пользователь: «Нужно оценить запасы по объекту».
2. Агент предлагает продукт «Подсчёт запасов / ПТД».
3. Агент показывает 2–3 исполнителей с объяснением (рейтинг, компетенции).
4. Кнопка «Сформировать ТЗ».
5. В конструкторе предзаполнены продукт, этапы, часть требований.
6. Пользователь отмечает «нужна 3D-модель».
7. Система показывает ready score + 2–3 риска.
8. Дозаполнение → выгрузка пакета документов.
9. На дашборде видно частые ошибки и востребованные продукты.

## 12. Риски (что может убить проект)

1. **Решить всё через LLM** — невоспроизводимо, сложно объяснить, плохо на грязных данных.
2. **Попытка покрыть весь каталог** — утонем в нормализации, демо станет поверхностным.
3. **Генерация только Word без структурированной модели** — не будет аналитики, ready score, ценности Кейса 2.
4. **Нет запасного плана по LLM** — если внешний API недоступен, нужна эвристика (keyword match) для демо.

## 13. План действий

1. Закрыть вопросы у экспертов (лаконичный список — отдельный файл).
2. Слой нормализации данных (единый справочник продуктов, пометка legacy, маппинг синонимов).
3. Спроектировать модель данных (RequestDraft + справочники).
4. Написать ЕДТ (требования, use cases, ограничения).
5. Правила проверки ТЗ (Rules Engine) + бизнес-правила ДО.
6. Тесты (API, UI).
7. Презентации ИК и АК.

---

## 14. 5 главных фактов

1. **Два модуля, один контур**: чат-бот → конструктор → выгрузка документов.
2. **Гибридная архитектура**: LLM понимает запрос, правила принимают решение.
3. **Ядро — структурированная заявка (RequestDraft)**, документы — её представление.
4. **Данные грязные**: нужен слой нормализации до разработки.
5. **MVP узкий и честный**: 3–5 продуктов, сквозной end-to-end сценарий.
